## Prioritized findings

### P1 — account identity can be written onto another player's inventory

`src/app/background.ts:167-170` changes the username and persists any held inventory with that name, without checking its `accountOwner`. Reproduction sequence: A's inventory is loaded; B's username arrives; B's inventory has not arrived yet. The store correctly still identifies A as owner, but the controller writes A's data with B's name. If the app restarts before B's inventory arrives, hydration treats this mislabeled snapshot as B's. A later partial B read can then merge with A's data.

The store probe confirmed the intermediate state: username B, owner A, A's credits. The disk mislabel is directly established by the controller call site; an IndexedDB restart simulation was not run. Fix ownership and inventory publication as one boundary, and test event ordering and restart between identity and inventory events.

### P1 — account switching retains another player's live progression

`src/core/store.ts:132-152` replaces inventory on a switch but never resets `liveClears`. `src/data/progression.ts:200` unions those clears into the current account. Probe: A clears SolNode1, switch to B, accept B inventory with an empty Missions array; `liveClears` still contains SolNode1. B can receive false completion and reachability advice. Clear or partition account-scoped transient state at the same boundary as inventory ownership.

### P1 — the visible storage-failure warning is disconnected

`src/app/Shell.tsx:119,138` reads `acquire.durable` to show “not saved.” `src/app/mirror.ts:43-56` does not copy `acquire` into either visible window. Its value stays at the local default even when the controller reports failed persistence. The warning exists but cannot report the background failure through the normal mirror path. Mirror the complete required data state and cover it with a cross-window contract test.

### P2 — controller reconnection is missing

`src/app/mirror.ts:60-75` retries only until its first connection, then subscribes permanently to that store. It never detects replacement of the controller store. If a visible window survives a background reload, it can retain a dead subscription. Startup failure also permanently gives up after 30 seconds with a console warning. This is a confirmed missing recovery path; the Overwolf reload scenario was not exercised live.

### P2 — cold-cache failures bypass the per-key retry floor

`src/core/gentle.ts:343` deletes the entry after an ordinary failure with no cached value. Unlike the 429 path, no next-attempt deadline remains. A subsequent caller immediately invokes the loader again, subject only to the token bucket. A probe with ttl/minInterval both 60 seconds made three immediate failing loader calls. Maintain attempt/backoff state separately from cached successful values.

### P2 — snapshot queue reports success before durability

`src/core/snapshot.ts:207-210` returns true when a write is merely queued. Callers use this boolean as successful disk persistence. Additionally, `rollDue` is cleared before the transaction commits (`:156`); an aborted transaction can consume the pending generation roll. These are source-confirmed semantics, not fault-injected IndexedDB reproductions. Resolve callers on the transaction covering their snapshot and update generation state only after commit.

### P2 — historical comparisons are not scoped to account ownership

`src/ui/useDelta.ts:39-40` reads the previous snapshot and discards its username; it reads only once at mount. The previous snapshot can belong to another account because `snapshot.ts` rolls snapshots across username changes. Arsenal comparisons can subtract one player's inventory from another's, or retain an old baseline when the current account changes. Compare only snapshots of the same owner and define session baseline invalidation explicitly.

### P2 — build tooling is not reproducible from package.json

ESLint is missing from devDependencies and unavailable to `npm run lint`. `eslint.config.mjs:1` imports an absolute global configuration under Administrator's profile. `npm run routes` uses undeclared `tsx`; packaging depends on separately installed `ow`. The scripts also execute TypeScript directly through Node without an engines requirement explaining the supported runtime. Declare and pin the required toolchain and keep lint configuration in the project.

### P2 — a normal Git add omits required app icons

`.gitignore:19` ignores every PNG, including all three existing manifest icon/splash assets under `public/icons`. `git check-ignore public/icons/icon-active.png` confirms the exclusion. There are no commits and all project files are untracked, so no tracked-file exception currently protects them. A future clone can build without those manifest assets. Narrow screenshot ignores and include the required source images.

### P3 — account freshness labels use mutation time

`src/app/Shell.tsx:123` chooses `inventoryAt` before `capturedAt` and ignores `answeredAt`. GEP deduplicates unchanged inventory, so a confirmed unchanged read need not update inventoryAt/capturedAt even though answeredAt advances. The “Account last read” label can become old while GEP is still confirming the account. Separate last-changed, last-confirmed, and last-persisted timestamps in presentation.

### P3 — test fixtures are shipped as public assets

`scripts/check-build.ts` loads its anonymized account fixture from `public/__review-acct.json`. The production build copies it to `dist/__review-acct.json`; this was verified. No claim is made that this anonymized fixture contains credentials. It is test-only data unnecessarily included in the distributed app and should live outside Vite's public directory.

## Product and maintenance concerns

- `docs/UX.md` specifies four coordinated surfaces with contextual drill-downs. `src/panels/panels.ts` implements 15 panels in six navigation groups. This is an objective specification/implementation divergence. Whether the specification should change or the UI should be rebuilt requires product judgment; this audit did not visually evaluate the current app.
- The background controller coordinates acquisition, persistence, mission attribution, planning and presentation. Many panel components also combine derivation, asynchronous orchestration and rendering. React Doctor flags 24 giant components and 37 complex React functions. The confirmed missing mirror field is an example of why explicit state contracts and narrower ownership matter more than simply splitting files.
- Comments and documents often present historical fixes as current guarantees. README says GEP getInfo is called exactly once per session, but `gep.refresh()` intentionally performs additional event-driven reads. README reports 54 scripts/769 assertions, while the current command has 57 scripts and this run emitted 815 `ok` lines. Historical measurement tables in QUALITY-BASELINE are not current UI evidence.
- Passing gates do not prove all integration paths: this audit found cross-module defects while the complete suite passed. Some catalogue-dependent checks explicitly exit successfully or return after a SKIP when input cannot be loaded (`check-optimise.ts:67-69`, `check-moddb.ts:114`, `check-fixture-paths.ts:144-147`). This run showed no skips, but CI should distinguish passed, skipped, and failed coverage.

## Recommended repair order

1. Establish one account-ownership transition contract across acquisition, snapshots, live clears, historical comparisons, and recorder attribution; test reversed event order and restart during the transition.
2. Repair visible-store propagation and controller reconnection, then exercise storage failure and background reload with surviving visible windows.
3. Repair persistence completion semantics and cold-cache backoff with fault-injection tests.
4. Make install/lint/check/package reproducible, track source assets, and separate test fixtures from shipped assets.
5. Run a live UI and gameplay acceptance pass covering cold start, offline planning, first/late account read, partial reads, account switch, modding open/close, resolution changes, and game exit.
6. Reconcile the interaction specification with the intended product and assess planner quality against verified game inputs. Mathematical correctness of the optimizer, market advice, and current game-data completeness remain substantial separate review areas.
